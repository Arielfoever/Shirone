# Internationalization Scope

- Every new `I18nKey` must have a non-empty value in all ten locale modules under `src/i18n/languages/`. Keep locale object keys synchronized with `src/i18n/i18nKey.ts`; the type check catches missing keys but does not prove that values are meaningful.
- Parameterized copy must preserve the exact placeholder-name set across locales, such as `{date}` or `{days}`. Replace placeholders in the consuming component or page; do not add a second ad-hoc translation system.
- When adding a supported language or alias, update the lookup map in `src/i18n/translation.ts` and verify fallback behavior. Keep the existing locale module naming and exported object shape.
- Do not put route-specific data, counts, dates, or user names into locale files. Pass those values into an existing localized template at the consumer and test the replacement path when it is user-visible.
- `i18n(key)` resolves its language through a three-step chain: (1) the request context installed by `src/utils/middleware.ts` (`AsyncLocalStorage` reader in `src/i18n/requestLocale.ts`) — this covers SSR requests and SSG page rendering, so `/zh/*` pages get Chinese copy; (2) `<html data-ui-locale>` in the browser (hydration and client-side tools read the SSR-frozen attribute); (3) `siteConfig.lang` as the build-time fallback for code with no request context (`getStaticPaths`, feed endpoints, config module evaluation). Consequently, never call `i18n()` at module top level in config or shared modules — the value would freeze at load time. Store `"$t:<key>"` references instead and resolve them at render time with `resolveI18nText()` (see `src/config/navBarConfig.ts` and its two consumers). Pass the explicit `{ lang }` option only for output that must stay language-stable across cache reuse (the Markdown field labels in `src/utils/markdown-processor.mjs` are the one sanctioned use).
- Language identifiers must be normalized before any dictionary or override lookup: use `getTranslation()` / `normalizeLang()` in `src/i18n/translation.ts` (`zh-CN`, `zh_cn`, `ZH-cn` → `zh_cn`). The request chain emits BCP 47 hyphen forms while the dictionary `map` uses underscore keys; a raw `map[lang]` lookup misses and **silently falls back to English** (this once left every `/zh/*` UI string in `en` even though the request locale was correct). Never hand-roll a lookup on raw language strings.
- The `<html data-ui-locale>` attribute (rendered by `src/layouts/Layout.astro` from `locals.locale`) is only correct because cross-language in-site navigation is forced to full page loads: Swup's `ignoreVisit` guard in `Layout.astro` skips its takeover when the target URL's language prefix (from `<html data-ui-lang-map>`) differs from the current one, with a `content:replace` reload fallback for back/forward navigation. Do not remove that guard or route around it (e.g. by adding same-document cross-language transitions) without also making the persistent shell re-render — it lives outside `#swup-container`.
- For i18n changes, run `npx.cmd astro check` and the focused page/component test that renders the new key. Check at least one non-default locale when the change affects layout-sensitive copy.
